## 1. 概述

本文档规定 AutoPrint 仪表盘每次上线新版本时的**版本记录规范**，确保团队成员能一致地追溯"这个版本改了什么、何时发布、由谁发布"。

### 分支与部署模型（2026-07-30 引入）

- **`develop`**：日常开发分支。所有功能开发、Bug 修复、进度提交都在此分支完成，可频繁 `git commit` / `git push`，**不会触发任何部署、不消耗额度**。
- **`master`**：生产分支。仅在"功能完整、准备发版"时，将 `develop` 合并进来，再**手动部署**到生产平台。
- **Netlify（主生产）**：使用免费版、需节省构建额度，已**关闭自动发布**并关闭 Branch Deploys / Deploy Previews；上线一律走仪表盘 `Deploys → Trigger deploy → Deploy project without cache`（或 CLI `netlify deploy --prod`）。主域名 https://autoprintreport.netlify.app。
- **Vercel（后备）**：同一份静态站点（`index.html`）同时部署到 Vercel 作为**故障切换 / 后备**。将同一个 GitHub 仓库（`autoprint-dashboard`）导入 Vercel 即可，产出与 Netlify 完全一致；当 Netlify 不可用或需切换时，用 Vercel 域名作临时入口（或改 DNS 指向 Vercel）。Vercel 同样建议关闭自动发布、按需手动部署以省额度。
- **关键纪律**：本地（http://127.0.0.1:5500/）看到 ≠ 线上已生效。每次发版必须打开线上 URL 验证（详见第 4 节「发版前确认已部署」）；Netlify 与 Vercel 两个环境都需分别确认已部署生效。

版本信息统一存放在 **Supabase `app_versions` 表**，并在仪表盘「📋 版本记录」Tab 中可视化展示。不依赖 GitHub Releases（纯 Web 应用无下载产物，Releases 不适用）。

  ------------------------------------------------------------------
  字段              类型              说明
  ---------------  ----------------  ----------------------------------
  version          TEXT (唯一)       语义化版本号，如 `1.2.0`
  released_at      TIMESTAMPTZ       发布日期时间（含时区）
  changes_summary  TEXT              变更摘要（一句话到一段，中文）
  commit_hash      TEXT (可空)       关联 git commit 短哈希，如 `3324419`
  deployed_by      TEXT (可空)       发布人
  created_at       TIMESTAMPTZ       记录创建时间（系统自动）
  ------------------------------------------------------------------

## 2. 版本号规则（语义化版本）

采用 `主版本.次版本.修订号` 三段式：

  ------------------------------------------------------------------
  变更类型          触发场景                         示例
  ---------------  --------------------------------  ---------------
  修订号 +1         缺陷修复、文案修正、小调整       `1.2.0` → `1.2.1`
  次版本 +1         新功能、新 Tab、可见增强         `1.2.0` → `1.3.0`
  主版本 +1         重大重构、架构变更、breaking     `1.2.0` → `2.0.0`
  ------------------------------------------------------------------

- 初始上线为 `1.0.0`。
- 版本号**一经发布不可修改**（`version` 字段设了 UNIQUE 约束）。写错只能新增一条修正记录。

## 3. 发布触发条件

满足以下任一情况即应发布并记录一个版本：

- 新功能合并到 `master` 并**手动部署到 Netlify 主生产环境**（按需同步 Vercel 后备）
- 修复了影响用户使用的 Bug
- 重大 UI/UX 调整、品牌规范更新
- 数据表结构变更（如新增/调整 Supabase 表）

**纯本地调试、未部署到生产**的改动**不需要**发版本。注意：`develop` 分支上的日常提交只是进度记录，**不算发布**，无需发版本。

## 4. 发布前检查清单

> ⚠️ 前两项为 **v2.0.0 复盘整改新增的强制步骤**（教训 L10 / A1、A4）：数据库改造类版本尤其必做，避免"前端做到一半才发现 RPC 缺字段"的返工。

  ------------------------------------------------------------------
  ☐  【接口契约盘点·强制】改造前列全前端将依赖的接口契约：所有 RPC 的返回字段、需要写权限的表/列、生成列清单，逐项确认齐全（如 v2.0.0 教训：`get_all_profiles` 缺 `site_scope` 导致用户管理页返工）
  ☐  【回滚三件套·强制】生产变更前置备：① 打版本回滚 tag（如 `v1.3.1-rollback`）；② 建快照/备份表（改前 `CREATE TABLE ... AS SELECT`）；③ 更新云端权威回滚清单文档；三项就绪方可动手
  ☐  代码已在 `develop` 开发完成，并经本地 Go Live 测试通过（http://127.0.0.1:5500/ 无控制台报错）
  ☐  `develop` 已 `git push` 同步到 GitHub（进度留痕）
  ☐  已 `git checkout master` → `git merge develop` → `git push origin master`
  ☐  Netlify 已手动部署完成：仪表盘 Deploys → Trigger deploy → **Deploy project without cache**（或 `netlify deploy --prod`）
  ☑  【发版前确认已部署】已打开 https://autoprintreport.netlify.app（主站）验证新功能/变更**确实生效**；若启用 Vercel 后备，也需打开其域名确认已同步部署（防止"本地有、线上缺"的分叉，本次踩坑根因）
  ☐  相关 GitHub Issue 已关闭（commit message 引用 Issue 号）
  ☐  提交哈希已确认（`git rev-parse --short HEAD`），待写入版本记录
  ------------------------------------------------------------------

## 5. 记录版本（二选一）

### 方式 A：仪表盘「📋 版本记录」Tab（推荐，日常用）

1. 用 **admin 账号**登录仪表盘。
2. 切到「📋 版本记录」Tab，点击右上角 **➕ 记录新版本**。
3. 填写弹窗：
   - **版本号**：如 `1.3.0`
   - **发布日期**：默认今天，可改
   - **变更摘要**：本次改了什么（参考第 6 节）
   - **Commit 哈希**：粘贴 `git rev-parse --short HEAD` 的输出
   - **发布人**：你的名字
4. 保存 → 列表即时刷新，全员可见。

> 非 admin 账号看不到「➕ 记录新版本」按钮（受 Supabase RLS 限制：登录用户可读，仅授权角色可插入）。

### 方式 B：SQL 直插（批量 / 补录历史用）

```sql
-- 在 Supabase SQL Editor 执行
INSERT INTO public.app_versions (version, released_at, changes_summary, commit_hash, deployed_by)
VALUES (
  '1.3.0',
  NOW(),
  '本次变更摘要（中文，一句话到一段）',
  '3324419',          -- git 短哈希
  'Eric Zhang'
);
```

> 复现/回滚脚本见仓库 `scripts/create_app_versions.sql`（含建表、RLS、初始种子）。

## 6. 变更摘要写法

### 6.1 标准格式：4 类分组模板（v2.0.0 起强制，对齐前端渲染器）

仪表盘「版本记录」Tab 使用轻量解析器 `parseSummaryToHtml()` 渲染摘要，**只有符合下面语法才会显示为分组卡片**，否则降级为纯文本（老版本 v1.0/1.1/1.2 即如此）。

语法规则：
- `## 类别标题`：识别 4 类，标题须含对应关键词之一
  - `新增功能`（关键词：新增 / 新功能）
  - `优化 & 运维`（关键词：优化 / 运维）
  - `缺陷修复`（关键词：缺陷 / 修复 / Bug）
  - `文档与规范`（关键词：文档 / 规范）
- `- 变更项`：每条一行
- `(#N)`：Issue 引用，自动渲染为可点击标签（**注意是英文半角括号**，非「Issue #N」）
- 总项数 > 6 自动折叠 + 「查看全部 N 项」按钮

**标准范例（v2.0.0）**：
```
## 新增功能
- 多站点支持：数据库三表加 site/site_scope 列，业务日唯一键升级为「业务日+站点」(#61)
- 前端站点视图切换（汇总/北京/上海），KPI/图表/明细/CSV 随站点重算 (#63)

## 优化 & 运维
- 转正 RPC 改造支持站点隔离，配套快照备份与越权测试，全程可回滚 (#61) (#63)
- 两站发版：Netlify 无缓存部署 + Vercel 自动构建，生产验证汇总 25 = 京 8 + 沪 17 (#64)
```

**好例子要点**：简洁、面向团队，说明"做了什么"，带 `(#N)` 引用，按 4 类归位。
**差例子**：`改了 index.html，加了一个函数，调了 supabase.from，修了 bug。` —— 无分组、无引用、写实现细节。

### 6.2 通用原则

- **简洁、面向团队**：说明"做了什么 + 为什么"，不写实现细节。
- 每条变更单条不要超过一行半。
- 历史 v1.0/1.1/1.2 为纯文本格式（无 `##` 标题），属兼容保留，不必回改。

## 7. 与 GitHub Issue 的协作

- 每个功能/修复对应一个 GitHub Issue。
- 提交时 message 引用 Issue：`feat: ... (Issue #21)`。
- 发布并记录版本后，**关闭对应 Issue**。
- 版本记录里的 `commit_hash` 可反向定位代码，形成"Issue → Commit → 版本"可追溯链。

## 8. 示例：一次完整发布流程

```
0) 【强制·改造前】接口契约盘点 + 回滚三件套（见第 4 节前两项）：列全 RPC 字段/RLS 权限/生成列；打回滚 tag + 建备份表 + 更新云端回滚清单
1) 在 develop 分支开发 → 本地 127.0.0.1:5500 测试通过
2) git add .
3) git commit -m "feat(#23): XXX 功能 ✅ 已在本地环境测试通过"
4) git push                              # 推到 develop，不部署、不烧额度
5) 重复 1-4 累积进度，直到功能完整
6) git checkout master
7) git merge develop --no-edit           # Windows PowerShell 5.1 不支持 &&，分条执行；--no-edit 防弹编辑器
8) git push origin master                # 代码上 master，但自动发布已关，尚未部署
9) Netlify 仪表盘 Deploys → Trigger deploy → Deploy project without cache   # 手动部署（主站）
10) 打开 https://autoprintreport.netlify.app 确认新功能已生效   ← 发版前确认已部署
11) （若启用 Vercel 后备）master 推送自动构建，打开 Vercel 域名确认同步生效
12) git rev-parse --short HEAD   →  得到 e.g. a1b2c3d
13) 仪表盘用 admin 登录 → 「版本记录」Tab → ➕ 记录新版本
    版本号: 1.3.0
    摘要:   ## 新增功能
            - XXX 功能上线，YYYY 能力增强 (#23)
            ## 优化 & 运维
            - 发布流程改进 ZZZZ (#23)
    Commit: a1b2c3d
    发布人: Eric Zhang
14) 关闭 GitHub Issue #23
```

## 9. 注意事项

- 版本号写错不要改历史，新增一条修正记录并在摘要注明。
- `commit_hash` 尽量填，便于回溯；不填也允许。
- 历史里程碑已预置：`1.0.0`(07-03) / `1.1.0`(07-08) / `1.2.0`(07-09)。
- 如需"对外正式发布"能力，未来可叠加 GitHub Releases（打 tag `v1.x.x`），通过 `commit_hash` 与 `app_versions` 关联，本期不强制。

### 9.1 v2.0.0 复盘补充（工具与环境坑）

来自复盘文档 `AutoPrint_v2.0.0部署复盘与经验教训_v1.0_Hunyuan-Hy`（完整版见云端资料库）：

- **PowerShell 5.1 不支持 `&&`**：git 多命令要分条执行或用 `;` 串联；`git merge` 加 `--no-edit`。
- **Supabase MCP 随机 `internal_error`**：网络层问题非语句错误；先跑 `SELECT 1` 探活，同一 SQL 重试 1-2 次；DDL / GRANT-REVOKE 报错率更高需多次重试。
- **生成列不可直接 INSERT**：`execution_date` 是生成列，插入用源列 `执行时间`；UUID 一律子查询动态取，禁止手抄。
- **数据对账验收法**：所有数据类功能的验收截图数字，必须有数据库 SQL 复核（如汇总 25 = 京 8 + 沪 17）才算通过。
- **看板状态变更复核**：改 Issue 状态前先查真实 item id，改后复核全部相关 Issue，避免误改。
